# 큐 쓰기 경합 실험 결과

## 요약

Linux에서 정식 360회가 모두 작업 256개를 완료해 H1을 채택한다. ToteDB mixed의 역할당 작업자 8/1 처리량 비율은 256B에서 0.812 [95% 신뢰구간 0.711, 0.885], 4,096B에서 0.761 [0.652, 0.881]이다. 각각 대응 표본 5쌍이며 두 구간의 상한이 2보다 낮아 H2도 채택한다. 관측 범위는 공개 Python 큐 사용 경로와 작은 작업 묶음이다. 엔진의 기본값과 설계는 바꾸지 않는다.

큐를 업무 데이터와 함께 저장할 때의 성능을 확인하려고 별도 부하를 사용했다. 기존 큐 벤치의 순차 enqueue와 공유 핸들 방식으로는 동시 생산자·소비자의 파일 쓰기 경합을 구분하기 어려웠다. 이 실험은 작업자마다 연결을 열고 저장 결과를 재개방해 검사했다. 공식 YCSB 부하와 결과를 합산하지 않았다.

## 데이터 처리

측정·계산 수치는 [summary.json](results/summary.json)의 `runs`, `aggregates`, `comparisons`, `totedb_mixed_worker_scaling`에서 가져왔다. 개수와 합계는 `runs`를 phase별로 세거나 더했다. 환경·실행 id·소스 SHA는 manifest와 환경 metadata에서 확인했다.

| 단계 | 수 |
|---|---|
| 정식 수집 폴더의 전체 실행 | 432회 |
| 정식 처리량 통계에서 제외한 사전 실행 | 72회 |
| 실패·timeout·불완전 실행 | 0회 |
| 실패나 이상치로 제거한 정식 실행 | 0회 |
| 정식 분석 | 360회 |
| 별도 프로파일 | 사전 3회와 분석 3회, 총 6회 |
| 정식 완료 작업 합계 | 92,160개 |
| 사전 완료 작업 합계 | 18,432개 |

사전 실행은 새로운 DB의 경로 확인이며 장시간 안정 상태의 예열을 뜻하지 않는다. 느린 반복도 보존했다. 한 반복이라도 실패하면 해당 조건의 엔진 비교를 금지하도록 했고, 이번 자료의 24조건과 SQLite 기준선 두 종류에 대한 비교 48개는 모두 `comparable`이었다.

처리량은 완료 작업 수를 시작 gate부터 마지막 작업자의 요청 종료까지의 `elapsed_s`로 나눴다. `setup_s`에는 입력 검사, payload 생성, DB 설치, drain 사전 적재, 작업자 연결 준비가 포함되며 모두 gate 이전이었다. 공개 API 호출, payload 검증·결과 기록, commit, BUSY 재시도와 mixed의 빈 큐 대기는 요청 구간에 포함했다. 작업자 close와 재개방 audit는 처리량 분모에서 제외했다.

원자료의 `cleanup_s`와 작업자 `close_s`는 별도 종료 구간이다. `file_sizes.phase`는 `after_close`이며 작업자와 audit 연결을 모두 닫은 뒤 남은 DB·WAL·SHM 크기를 뜻한다. 실행 중 최대 WAL 크기나 디스크 쓰기량으로 해석하지 않았다. 종료·audit 세부 수치는 summary의 집계 항목이 아니므로 이 보고서에 별도 통계로 싣지 않았다.

## 가설 검증

| 가설 | 지표 | 값 | 사전 지정 신뢰구간 | n | 판정 |
|---|---|---|---|---|---|
| H1 | 정상 완료와 재개방 저장 검사 | 360/360회 성공, 실행마다 256개 완료, 오류·검사 문제 0건 | 해당 없음. 계획된 실행 전수 검사 | 360회 | 채택 |
| H2, 256B | ToteDB mixed 작업자 8/1 처리량 비율 중앙값 | 0.812 | 95% [0.711, 0.885] | 대응 5쌍 | 채택 |
| H2, 4,096B | ToteDB mixed 작업자 8/1 처리량 비율 중앙값 | 0.761 | 95% [0.652, 0.881] | 대응 5쌍 | 채택 |

H1의 성공은 수집기의 전체 ID·payload·상태·fence·attempts·업무 행 검사와 재개방 검사에 따른 판정이었다. 사전 실행도 72/72회 성공했지만 H1의 정식 분모에는 넣지 않았다. [독립 검증](validation/queue-verification.json)은 저장된 완료 ID와 payload를 직접 대조하고 입력 payload·행 digest·업무 digest를 재구성했다. 원자료와 파일 해시 검사, summary JSON·CSV 재생성 일치도 확인했다. 독립 검증의 판정은 주의사항 포함 통과였다. 기존 native library를 Python 모듈 import에만 사용했고 DB 재개방 실측을 새로 수행한 검증은 아니었다.

H2는 같은 payload와 반복 번호의 작업자 8/1 비율을 먼저 계산한 뒤 중앙값을 구했다. seed 226으로 대응 비율을 10,000회 재표집한 percentile bootstrap 구간을 사용했다. 상한이 2 미만이면 채택, 하한이 2 이상이면 기각, 나머지는 보류하는 사전 기준을 적용했다. 두 payload는 다중 비교 보정 없는 탐색적 개별 판정이다.

## 추가 분석

### 연산 지연과 경합

mixed, payload 256B, 역할당 작업자 8명의 연산별 p95를 대조했다. 아래 값은 실행별 p95의 정식 5회 중앙값 [최소, 최대]이며 단위는 µs다. 전체 실행의 표본을 합친 p95와 다르다. 모든 조건의 p50·p95·p99와 반복 범위는 summary의 `latency_s`에 보존했다.

| 엔진 | put p95 | claim p95 | ack p95 |
|---|---|---|---|
| totedb | 1910.9 [1299.1, 8455.2] | 2367.2 [656.6, 16548.3] | 613.6 [556.3, 673.5] |
| sqlite-wal | 1871.8 [591.7, 3771.6] | 2150.6 [431.8, 3026.7] | 503.7 [375.3, 551.6] |
| sqlite-delete | 2221.4 [1719.0, 4046.0] | 1748.0 [1061.1, 4742.5] | 1027.1 [1011.7, 1179.4] |

정식 실행 전체에서 발생한 BUSY와 EMPTY를 아래에 합산했다. 부하별 작업 계약이 달라 이 합계를 처리량 순위로 사용하지 않았다. BUSY는 미적용 연산의 재시도 횟수이며 실패 작업 수가 아니다. EMPTY는 빈 claim 응답이며 완료 작업으로 세지 않았다.

| 엔진 | BUSY 합계(건) | EMPTY 합계(건) | 작업자 오류(건) |
|---|---|---|---|
| totedb | 11,636 | 4,868 | 0 |
| sqlite-wal | 8,750 | 5,090 | 0 |
| sqlite-delete | 15,346 | 7,075 | 0 |

재시도 대기 시간과 작업자별 완료 분포·Jain 지수는 `runs.retry_sleep_s`와 `runs.worker_fairness`에 남겼다. 미적용 BUSY만 같은 정책으로 재시도했고, 결과가 불확실한 commit 오류를 전체 연산 재실행으로 숨기지 않았다. mixed는 생산자의 요청 종료와 소비자의 최종 ack 종료를 작업자별로 기록했다.

프로파일 폴더에는 CPU·최대 RSS·phase 원자료와 `python.prof`, `python-profile.json`, `sampling.json`을 보존했다. cProfile 범위는 controller thread이며 worker의 Python 호출과 native 엔진 stack을 제외했다. Linux에서는 기존 macOS sample 수집을 지원하지 않았다. 따라서 위 진단 실행은 엔진 내부의 mutex·fsync·GIL 중 어느 비용이 병목인지 확정할 근거가 아니었다.

### 수집 도구의 회귀 검증

[수정 후 독립 검증](validation/independent-evidence-fix.json)은 주의사항 포함 통과였다. 실제 child가 부분 JSON을 쓰다가 종료하는 사례와 합성 invalid UTF-8을 검사했다. 같은 증거 디렉터리에 정상 stdout을 쓴 뒤 다시 읽는 동작도 확인했다. 전체 collect 일정 중간에 잘린 worker 출력을 주입한 종단 간 검증은 아니었다. [수정 전 검증](validation/independent-verification.json)의 실패 기록은 그대로 남겼다. 축소 정확성 시험의 시간은 성능 자료로 사용하지 않았다.

## 해석

ToteDB는 이 작업량에서 mixed의 역할당 작업자를 늘려도 완료 처리량이 두 배로 늘지 않는다. 두 payload에서 작업자 8/1 비율의 구간 전체가 1보다 낮다. 단일 writer와 동기 commit에 따른 확장성 제한이라는 계획의 예측과 맞는 관측이지만, 원인별 비용을 분해한 결과는 아니다.

조건별 표에서는 SQLite WAL의 중앙값이 ToteDB보다 높다. 다만 256B enqueue의 작업자 4·8 조건은 대응 비율 구간에 1이 포함된다. ToteDB의 중앙값은 SQLite DELETE보다 높다. 이 비교는 설정을 맞춘 공개 Python 사용 경로의 관측이며 DB 전체의 승자 판정으로 확장하지 않는다. native 병목을 확인하지 못해 원인과 일반적인 도입 우위는 판정할 수 없다.

SQLite 양쪽에 문장 cache와 상태 색인을 적용하고 WAL/FULL을 기준선에 포함했다. ToteDB의 ctypes 큐 API와 SQLite의 sqlite3 SQL 구현은 바인딩·SQL 처리·객체 변환 비용이 다르다. 연결별 commit이라는 사용 계약도 처리량에 영향을 준다. 배치 commit, 다중 프로세스, 장기 적체량을 바꾼 도입 판단에는 별도 자료가 필요하다.

업무 행과 큐 입력을 같은 트랜잭션에 넣는 outbox의 관측과 재개방 검사는 큐 용도의 근거다. [YCSB 결과](../ycsb-sqlite/report.md)의 E 스캔 성능과는 작업 계약이 달라 점수나 처리량을 합산하지 않는다. 이번 결과는 엔진이나 기본값의 변경 근거로 사용하지 않았다.

| 내구성 설정을 전원 장애 증명으로 오해 | DURABLE·FULL 조건의 정상 종료와 재개방을 확인했다. 전원 장애·다중 프로세스·외부 exactly-once 보장은 미검증이다. |

## 한계

- 작업 256개의 단일 프로세스·다중 스레드 합성 부하다. 운영 큐의 장시간 적체·worker 처리 업무·외부 시스템 왕복을 재현하지 않는다.
- 조건당 정식 5회이며 검정력으로 표본 수를 정하지 않았다. 작은 표본의 bootstrap 구간은 정밀한 모집단 보장을 주지 않는다.
- 엔진 시작 순환으로 시간 편향을 줄였지만 workload 순서와 VM 공유 host의 잡음은 남는다. Mac과 Linux의 성능 차이를 계산할 자료는 없다.
- cProfile은 controller thread만 관측한다. native 병목이나 부하 생성기 포화를 확정하지 못한다.
- CPU는 프로세스 누적 값이고 최대 RSS는 프로세스 최고치다. 파일 크기는 `after_close`의 잔존 크기다. 요청 구간만의 자원 비용이나 실행 중 최대 WAL로 해석하지 않는다.
- 전원 장애, 강제 종료 뒤 DB 복구, 다중 프로세스 경합, 외부 부작용의 exactly-once 처리는 정식 수집에서 검증하지 않았다.
- 고정 시계의 정상 부하는 lease 만료·재전달을 제외한다. 부분 stdout 처리 시험도 전체 collect 중간에 실패를 주입한 종단 간 시험은 아니다.

## 재현 방법

원자료를 다시 분석하려면 실제 큐 소스와 [데이터 설명](data/README.md)의 파일을 준비한다. 요청 부하를 다시 실행하는 `collect`와 저장된 자료의 재검증을 구분한다. 아래 명령은 실험 폴더에서 실행하며 새 검사용 로그를 남긴다.

```sh
RUN_ID=20261019T031416Z-b590d61-check ./run.sh verify
RUN_ID=20261019T031416Z-b590d61-check ./run.sh analyze
python3 ../../../bench/queue_contention/run.py verify --output profile
```

`verify`는 manifest의 파일 집합·해시·조건 조합·입력 식별자를 검사하고 summary JSON·CSV를 메모리에서 재생성해 바이트 단위로 비교한다. `analyze`는 원자료를 다시 읽어 결과 파일을 쓴다. DB를 열어 새 성능 수치를 수집하는 명령은 아니다. 수집 당시 DB 경로가 없는 환경에서도 보존된 원자료로 검증할 수 있다. 분석 모듈 import에 맞는 native library는 필요하다.

새 Linux 수집은 [Linux 재측정 계획](linux-design.md)의 고정 소스와 CI 실행 방식을 따른다. 수집 전 빌드를 마치고 측정 중 다른 빌드·시험을 실행하지 않는다. 기존 raw·manifest·명령 로그를 덮어쓰지 않는다. 원자료는 정본이며 summary JSON·CSV는 생성물이다. summary를 지워도 원자료로 재생성할 수 있지만 raw와 manifest를 잃으면 이 실행의 재검증 근거도 잃는다.

## 단일 writer 후속 비용 평가

### 요약

후속 H2 카탈로그 직접 복제와 H3 캐시 버퍼 재사용의 누적 처리량 개선은 입증하지 못했다. 대응 처리량 비 중앙값은 workers 1에서 0.999930, workers 8에서 1.002200이며 두 bootstrap 95% 구간 모두 1을 포함했다. 각 조건은 대응 5쌍이다. 정확성 검사는 통과했지만 성능 채택 기준을 충족하지 않아 두 제품 최적화 후보를 철회했다. 개선이 없다는 동등성 증명이나 모든 부하의 성능 판정은 아니다.

이 절의 비용 가설 H1·H2·H3·H4는 위 정식 360회 실험의 완료·확장성 가설과 별개다. 기존 결과와 원자료는 바꾸지 않았다. 수치는 별도 생성물 [단일 writer 비용 요약](results/single-writer-cost.json)에 있다.

### 계획과 다른 점

첫 도구 실행 `39206644421`은 perf 실행 파일을 찾지 못했다. `45be867c`에서 패키지 설치 경로·심볼릭 링크 탐색을 보완한 뒤 [CI 39208276725](https://github.com/woonyong-choi/totedb/actions/runs/39208276725)부터 실제 CPU stack을 수집했다. 첫 도구의 미계측 상태와 syscall system time은 후속 wall-clock 진단으로 바꾸어 기록하지 않았다.

후속 추적은 설정·종료·재개방 audit를 포함한 전체 프로세스 범위다. 요청 구간만의 비용이 아니다. Linux의 before/after 최대 RSS가 이전 프로세스의 고수위 값을 물려받는 현상을 확인해 엔진 메모리 우위의 근거로 사용하지 않았다. 정식 표본이나 사전 채택 기준은 변경하지 않았다.

누적 비교의 중앙값은 높아졌지만 반복 범위는 겹쳤다. H3 추가 비교의 workers 1에서는 claim p99 중앙값이 낮아졌으나 다른 조건까지 일관된 지연 개선으로 판정하지 않았다. tail 회귀 가능성으로 기록하며 확정 회귀나 사후 비열등성 판정으로 사용하지 않았다. BUSY·재시도와 소비자 완료 분포도 일관된 공정성 개선을 입증하지 못했다.

카탈로그 복제 하위의 encode/decode 제거와 세대 전환의 캐시 본문 재할당 제거는 코드·단위 시험으로 확인했다. 이는 실제 큐 처리량 향상과 별개다. CPU 추적에서도 clone 하위 decode 제거와 저장 encode 유지가 부합했다. 미샘플 함수는 비용 0으로 보지 않았고, 누적 thread syscall wall-clock 시간을 elapsed의 비율로 환산하지 않았다.

### 해석과 한계

처리량·CPU·지연을 구분한 단일 writer 평가다. H2의 한 조건에서 작은 개선 신호가 있었지만 H3 추가 효과와 누적 효과는 사전 기준을 충족하지 못했다. 따라서 성능 최적화로 채택하지 않고 제품 변경을 철회했다. 진단 도구·독립 소유권·실패 보존 회귀 시험은 유지했다. 실험 후보 `65a20bed`와 `106bdbac`, 원본·실패 로그·DB는 보존했다.

후보의 Linux sanitizer·패키지 검사와 fresh 로컬 UBSan C 38개·예산 검사 54개는 통과했다. Python은 45개 통과, 참조 패키지 부재 4개는 건너뜀으로 남겼다. 제품 후보 철회 후 실행 코드가 `45be867c`와 같음을 대조하고 fresh UBSan C 36개를 다시 통과했다. 정확성 통과가 성능 채택을 뜻하지 않는다.

작업 4,096개의 합성 부하와 조건별 5회, 고정 시계, 정상 commit·재개방 범위다. 큰 장기 적체·실제 외부 처리·전원 장애·DB 전체의 우위를 증명하지 않는다. 바인딩과 튜닝 차이도 남는다. 다중 writer 도입과 충돌·대량 갱신·복구 위험은 [후속 이슈 #238](https://github.com/woonyong-choi/totedb/issues/238)에 남겼으며 이번에는 구현하지 않았다.
