# 배포판 다각도 비용: 실험 계획

| 항목 | 값 |
|---|---|
| 추적 | [#242](https://github.com/woonyong-choi/totedb/issues/242) |
| 관련 설계 | [아키텍처](../../architecture.md), [빌드와 시험](../../build-and-test.md) |
| 사전 데이터 | 기존 YCSB·큐·H2/H3 평가와 0.2.0의 N=12 정확성 검사를 확인했다. 새 Linux 표본과 합산하지 않는다. |

## 목적

ToteDB 0.2.0의 비용을 단일 C 클라이언트, 공식 YCSB 바인딩, 실제 큐 업무라는 서로 다른 경계에서 측정한다. 비계측 성능과 계측 진단을 분리하고 다음 비용 가설을 판단할 근거를 남긴다. 제품 최적화와 새 배포는 수행하지 않는다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | 비계측 정식 실행 전부에서 오류·완료량·재개방 저장 검사 불일치가 없다. | native OFF 30회·YCSB 120회·큐 240회 |
| H2 | 계측 native 실행 전부에서 요청당 begin·exec·commit 기록이 있고 drop·불완전 기록이 없다. | native ON 정식 30회 |
| H3 | 비계측 라이브러리에 계측 심볼이 없고, ON 라이브러리에는 계측 심볼과 TLS가 있다. | 수집에 실제 사용한 두 빌드 |

성능 비율은 탐색적 추정이다. 최고 수치를 고른 합격선, DB 전체의 승자, 최적화의 인과 효과는 판정하지 않는다.

## 비교 조건

| 항목 | 값 |
|---|---|
| native | 동일 UPDATE·명시적 begin/update/commit·DURABLE/FULL, ToteDB·SQLite prepare-each·SQLite prepared-reuse |
| YCSB | 공식 0.17.0 Client의 A~F, 동일 Java/JNI SQL 바인딩, 기존 자동 commit·prepare-each 정책 |
| 큐 | enqueue·drain·mixed·outbox, ToteDB·SQLite DELETE/FULL·WAL/FULL, SQLite 문장 cache 128 |
| 실행 순서 | native는 반복별 엔진 시작 순환과 ON/OFF 교대, 나머지는 기존 수집기의 반복별 엔진 시작 순환 |
| 평가 방식 | 실제 반환값·저장 결과 자동 검사, 사람 평가·맹검 해당 없음 |

prepared-reuse의 최초 prepare는 측정 밖이다. ToteDB에는 새 prepared API를 추가하지 않는다. YCSB F는 기존 바인딩대로 read와 update 각각 자동 commit이며 원자적 read-modify-write가 아니다. 큐 mixed의 workers 1은 생산자 하나와 소비자 하나여서 경합 없는 단일 C 클라이언트와 다르다. 모든 조건에서 ToteDB의 실제 쓰기 트랜잭션은 한 번에 하나다.

## 측정 지표

| 지표 | 종류 | 정의 | 단위 |
|---|---|---|---|
| native 처리량 | 계산 값 | 완료 UPDATE 수 / begin·prepare·exec·commit·출력 처리 시간 합 | UPDATE/s |
| native 단계 시간 | 측정 값 | 요청의 inclusive·exclusive wall/thread CPU 시간 | ns |
| I/O | 측정 값 | 성공한 syscall 반환 바이트·시도·오류·짧은 I/O·EINTR | byte·회 |
| YCSB 처리량·지연 | 측정 값 | 기존 수집기의 논리 operation 경계와 연산별 지연 | ops/s·μs |
| 큐 처리량·지연 | 측정 값 | 기존 수집기의 완료 업무 단위와 put·claim·ack 등 요청 경계 | jobs/s·s |
| 오류·재시도·저장 검사 | 측정 값 | 기존 audit·실제 완료량·BUSY·EMPTY·timeout·payload·fence·업무 행 검증 | 회 |
| 비율·반복 변동 | 계산 값 | 같은 조건·반복끼리 대응한 처리량 비, 중앙값·최솟값·최댓값·bootstrap 구간 | 비율 |

native 처리량 단위는 UPDATE/s다. 세 처리량을 하나의 점수로 합치지 않는다. syscall 성공 바이트는 물리 장치 쓰기량이 아니다. exclusive 시간을 사용해 중복을 피하고, wall에서 CPU를 뺀 잔여를 fsync나 OS off-CPU 비용으로 단정하지 않는다. SQLite 내부 단계는 관측하지 못했으므로 unknown이며 0이 아니다.

## 표본

| 항목 | 값 |
|---|---|
| 출처 | 기존 driver·공식 YCSB Client·자체 큐 수집기 |
| 크기 | native 정식 60·사전 12회, YCSB 정식 120·사전 24회, 큐 정식 240·사전 48회 |
| 크기 근거 | 조건당 대응 5쌍의 수집 한도, 검정력 기반 표본 수 산정 아님 |
| 중단 규칙 | 실행당 180초·job 45분, 실패·부분 결과를 보존하고 가능한 다음 조건 계속, 속도에 따른 조기 중단·표본 대체 없음 |
| 반복과 예열 | 조건당 새 프로세스 사전 1회·정식 5회, 사전 실행은 정식 추정에서 제외 |

정식 420회 중 비계측 성능 표본은 390회이고 계측 진단은 30회다. 사전 84회는 JVM·프로세스·저장 경로의 짧은 사전 실행이며 모든 캐시가 정상 상태에 도달했음을 보장하지 않는다.

## 분석 방법

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | 오류·완료량·저장 검사 | 계획한 비계측 matrix 전수 검사 | 390/390회 성공이면 이 실행 범위에서 채택, 오류가 하나라도 있으면 기각, 미수집은 보류 |
| H2 | ON 요청·손실·불완전 | 정식 30회 각각 3N 요청과 손실 표시 검사 | 전부 일치하고 손실·불완전 0이면 채택, 불일치면 기각, 미수집은 보류 |
| H3 | 실제 binary 심볼·TLS | 수집 전에 검사하고 빌드 해시 기록 | OFF 제외·ON 대조군 모두 통과하면 채택, 실패하면 성능 비교 무효 |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 사전 실행과 ON 진단만 비계측 성능 통계에서 제외, 느린 표본의 이상치 제거 금지 |
| 실패한 실행 | 횟수·원인·부분 결과·DB 보존, 해당 비교를 incomparable로 표시, 실패의 분모 제외 금지 |
| 성능 추정 | 조건별 중앙값·범위, 같은 반복의 비율 5개와 그 중앙값, percentile bootstrap 10,000회·95% 구간 |
| 다중 비교 | 성능 비교는 모두 탐색적·명목 95% 구간, 여러 구간을 골라 통계적 우위나 전체 가설 채택 주장 금지 |
| 독립성 | 같은 VM의 반복은 공유 host 영향을 받으며 독립 장비 표본이 아님, bootstrap은 반복 변동의 기술적 추정 |
| 정확성 불확실성 | 계획 matrix의 전수 관측값으로만 보고, 독립 Bernoulli 모집단의 오류율 신뢰구간으로 일반화 금지 |
| 유효 숫자 | 처리량 소수 둘째 자리, ms 환산 지연 셋째 자리, 비율 넷째 자리, 원본 정밀도는 JSON에 보존 |
| 재현 | 원자료 해시·저장 검증 후 analyze 재실행의 summary 바이트 일치 확인 |

## 추가 분석

- 비용 단계·SQLite 준비 문장 재사용·payload 증가·worker 증가의 효과를 서로 다른 축으로 설명한다.
- 기존 0.1 계열 YCSB·큐와 수치를 나란히 읽을 수 있지만 장비·규모·소스가 달라 변화율이나 회귀 판정으로 사용하지 않는다.

### 원인과 가설의 기록

보고서는 문제 관측, 근거, 원인 가설, 실험 선택, 결과, 판단 변경, 남은 반례를 연결한다. 역사적 비용 가설 H1~H4와 이번 정확성·계측 가설 H1~H3는 별도 표로 구분한다. 수집 후 새로 생긴 원인 가설은 탐색적 가설로 표시하고 이번 표본으로 사전 검증됐다고 주장하지 않는다. 시간의 동시 관측·상관·인과 확인을 구분하며 확인하지 못한 원인은 미확정으로 남긴다.

## 위험 요소와 대응

| 위험 요소 | 대응 |
|---|---|
| 공유 VM·host 부하와 실행 순서 | 환경 전후 기록·엔진 시작 순환·대응 반복·범위 공개 |
| 계측이 원래 비용을 바꿈 | ON/OFF 별도 실행, 정식 성능은 OFF만 사용 |
| 바인딩·prepare·트랜잭션 경계 차이 | C API·Java/JNI·Python 큐를 별도 질문으로 구분 |
| 작은 표본·짧은 backlog | N·표본 수·캐시 한계 공개, 큰 운영 DB·장시간 서비스로 일반화 금지 |
| 내구성 설정과 보장의 차이 | FULL·DURABLE 조건 공개, 전원 장애 동등성 주장 금지 |
| 실패나 원자료 소실 | 항상 artifact 업로드, JSON·DB·실패 stderr·해시 보존 |
