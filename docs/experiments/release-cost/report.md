# 배포판 다각도 비용: 실험 결과

## 요약

비계측 정식 390회와 별도 계측 진단 30회가 모두 완료·반환·저장 검사를 통과했다. 사전 실행 84회도 실패가 없었다. 정확성·계측 가설 H1~H3를 관측 범위에서 채택한다. 제품 변경은 하지 않았다.

단일 행 UPDATE와 실제 큐의 상대 성능은 달랐다. native OFF의 N=1,024에서 ToteDB/SQLite prepare-each 처리량 대응 비 중앙값은 2.5374 [탐색적 95% 구간 2.4209, 2.5648]이었다. 반면 mixed·256B·역할별 workers 1의 ToteDB/SQLite WAL 대응 비는 0.5930 [0.5610, 0.6112]이었다. 한 미시 시험의 결과로 DB 전체나 큐의 우위를 설명할 수 없다.

수치는 [실측 요약](results/summary.json), 초기 중단·출처는 [실행 출처](results/provenance.json)에 있다. 과거 결과와 이번 자료를 합산하지 않았다.

성능 비율은 가설 채택표와 구분한 탐색적 추정이다. 모든 비율 구간은 조건마다 대응 5쌍의 명목 95% bootstrap 구간이며 다중 비교 보정을 하지 않았다. 반복별 비율의 중앙값은 두 처리량 중앙값을 나눈 값과 다를 수 있다.

### 단일 C UPDATE와 준비 문장 정책

각 칸은 비계측 처리량 중앙값 [최소, 최대]이며 단위는 UPDATE/s다. 새 프로세스·새 DB에서 정수 한 행을 증가시키고 매회 명시적 begin/update/commit을 수행했다.

| N | ToteDB | SQLite prepare-each | SQLite prepared-reuse |
|---|---|---|---|
| 128 | 3634.44 [1729.85, 3880.38] | 1254.94 [1199.54, 1404.03] | 1161.87 [749.02, 1465.52] |
| 1,024 | 3486.46 [3391.36, 3525.26] | 1380.28 [1343.83, 1440.17] | 1353.82 [1061.36, 1424.58] |

| N | 기준 | ToteDB/기준 대응 비 | 95% 구간 |
|---|---|---:|---|
| 128 | SQLite prepare-each | 2.8488 | [1.2321, 2.9929] |
| 128 | SQLite prepared-reuse | 2.5613 | [1.2588, 5.1806] |
| 1,024 | SQLite prepare-each | 2.5374 | [2.4209, 2.5648] |
| 1,024 | SQLite prepared-reuse | 2.5938 | [2.4474, 3.3190] |

SQLite는 DELETE/FULL이다. WAL과의 native 비교는 수행하지 않았다. prepared-reuse의 최초 prepare는 측정 밖이다. 이 설정에서 재사용의 처리량 우위를 입증했다고 해석하지 않았다. 짧은 반복의 변동과 commit 비용이 남는다. 각 타이머·반복 원값은 요약에 있다.

### 내부 비용과 측정 자체의 영향

ON/OFF의 ToteDB 대응 처리량 비는 N=128에서 0.9695 [0.6270, 1.9640], N=1,024에서 0.9051 [0.8704, 0.9244]이었다. 계측 실행의 비용을 무시할 수 있다고 취급하지 않았고 정식 성능의 대용으로 사용하지 않았다.

| ON ToteDB N=1,024의 단계 | exclusive wall 중앙값 ns/실행 | exclusive thread CPU 중앙값 ns/실행 |
|---|---:|---:|
| fsync | 259599903 | 23989495 |
| 메타데이터 | 12999949 | 12972959 |
| pwrite | 10406737 | 10485749 |
| parse | 3316017 | 3353213 |

fsync는 이 단일 행 UPDATE에서 가장 큰 관측 wall 구간이었다. syscall 성공 바이트는 UPDATE당 pread 16,384B, pwrite 40,960B였고 시도는 각각 2회와 5회, fsync는 1회였다. 이를 물리 장치 쓰기량이나 전원 장애 내구성과 동일시하지 않는다. 단계별 중앙값을 합산해 전체 시간을 재구성하지 않았다. wall과 thread CPU의 차이는 미분류 잔여이며 별도의 가산 비용이 아니다.

## 원인 가설의 형성과 변화

이 절은 새 실측 전에 확인한 기존 실험의 판단 흐름이다. 과거 표본을 이번 결과에 합산하지 않는다. 각 관측이 어느 가설을 뒷받침하는지와 무엇을 아직 설명하지 못하는지를 구분한다.

### 범위 조회에서 시작한 문제

최초 [YCSB 비교](../ycsb-sqlite/report.md)에서는 모든 부하가 같은 양상으로 느리지 않았다. 읽기와 쓰기를 섞은 부하의 순위만으로 엔진 전체를 평가하면 범위 조회의 큰 차이를 놓친다. E의 낮은 처리량과 SCAN 지연을 구분해 보면서 TEXT 기본 키 범위 조회의 실행 경로를 조사했다.

당시 근거는 workload 결과, 실제 반환 행·바이트 검사, 별도 CPU 관측과 코드 경로였다. 전체 행을 읽고 정렬하는 경로가 관측됐고, 범위 밖 행을 읽지 않아도 되는 요청에서도 그 비용을 지불한다는 가설을 세웠다. 프로파일의 특정 함수가 보였다는 사실만으로 전체 시간의 기여율을 계산하지는 않았다.

[TEXT 색인 실험](../text-range/report.md)은 같은 VM의 전후 비교와 SQLite 대조군으로 이 가설을 검증했다. 색인 하한에서 순회하고 안전한 기본 키 오름차순 정렬에서 필요한 결과를 얻으면 중단하도록 바꿨다. 결과 소비·저장 검사와 경로 검증을 통과했고 해당 E 조건의 개선이 관측됐다. 출력 별칭이 원본 기본 키를 가릴 때 정렬을 잘못 생략하는 중간 구현의 회귀도 재현해 고쳤다. 이 회귀는 원래 baseline의 실패가 아니었다.

판단은 범위 밖 전체 스캔·정렬을 줄이는 변경의 채택이었다. SQLite보다 모든 SQL에서 빠르다거나, 이 개선 비율이 큐에도 적용된다는 결론은 내리지 않았다. Mac 사전 timeout과 Linux 성공을 합치지 않았고, 당시 로컬 자원 압박을 timeout의 유일한 원인이라고 확정하지 않았다.

### 큐의 병렬 요청을 단일 writer와 구분

[큐 경합 실험](../queue-contention/report.md)은 여러 클라이언트가 쓰기를 요청하는 것과 여러 쓰기 트랜잭션이 동시에 진행하는 것을 구분했다. ToteDB는 실제 writer가 하나다. mixed에서 역할별 worker를 늘려도 쓰기 트랜잭션이 병렬로 실행되는 것은 아니다.

따라서 worker 증가가 처리량 증가로 이어지지 않는 관측을 즉시 교착이나 잘못된 구현으로 해석하지 않았다. 직렬화, BUSY 재시도, 짧은 backlog, Python 호출 경계, 작업 분배와 저장 비용이 함께 영향을 줄 수 있다. 다음 비용 가설을 분리했으며 하나의 원인이 확정됐다고 선언하지 않았다.

| 역사적 비용 가설 | 처음 의심한 이유 | 반증하거나 좁힐 근거 | 당시 판단 |
|---|---|---|---|
| H1 반복 SQL 해석 | 큐 업무가 비슷한 SQL을 여러 번 실행 | 요청별 파싱 시간과 준비 문장 정책을 통제한 비교 | 공개 prepared API·파서 cache 구현 보류 |
| H2 카탈로그 복제·저장 | 요청마다 작업 카탈로그와 인코딩·복원 경로 사용 | 직접 복제가 정확성을 보존하고 최종 처리량까지 개선하는지 | 실험 후보를 만들었으나 최종 채택 철회 |
| H3 세대 전환·캐시 | 세대 전환의 reload와 캐시 본문 재할당 관측 | 버퍼 재사용이 추가·누적 처리량과 지연을 개선하는지 | 실험 후보를 만들었으나 최종 채택 철회 |
| H4 쓰기·동기화·잠금 | durable commit과 파일 잠금·I/O 호출 사용 | 같은 요청의 단계별 wall·CPU·호출량·성공 바이트 연결 | 내구성을 바꾸지 않고 진단 근거 추가 필요 |

이 표의 H1~H4는 이번 계획의 정확성·계측 H1~H3와 다른 식별자다.

### H2 후보를 만들고도 채택하지 않은 이유

카탈로그 직접 복제 후보는 encode/decode를 통한 복제를 직접 소유권 복사로 바꾸는 시도였다. 단위 수준에서 불필요한 변환을 제거할 수 있어도 포인터 독립성, 할당 실패, 예산 계상과 호출자 상태 보존을 깨뜨리면 사용할 수 없다. 먼저 그 계약을 검사했고 실제 큐의 완료·payload·저장 결과도 확인했다.

기계적 작업 제거와 프로파일의 하위 decode 제거는 가설의 메커니즘에 부합했다. 그러나 저장 시 encode는 남았다. 일부 조건의 작은 처리량 신호만으로 전체 비용의 주원인이 복제라고 결론내릴 수 없었다. [후속 비용 평가](../queue-contention/report.md#단일-writer-후속-비용-평가)에 추가·누적 비교와 불확실성을 남겼다.

판단 기준은 내부 함수가 덜 호출되는지가 아니라 비계측 업무 처리량·지연·정확성이었다. 정확성이 통과했다는 이유로 성능 후보를 채택하지 않았다.

### H3 후보와 누적 비교가 판단을 바꾼 과정

H3는 캐시의 유효성 검사를 생략하는 변경이 아니었다. 세대 전환에서 캐시 본문 버퍼를 다시 할당하는 일을 줄이되, 다시 읽어야 하는 상태와 일관성 검사는 유지했다. H2 기준에 대한 추가 효과와 원래 기준선에 대한 누적 효과를 별도로 측정했다.

추가·누적 처리량 개선은 채택 근거로 충분하지 않았다. 반복 구간의 겹침과 tail 변동이 남았고 공정성 개선도 일관되게 입증하지 못했다. 따라서 두 제품 후보를 철회하고 계약 시험·진단 도구·실험 원자료는 유지했다. 이는 정확성 실패에 따른 철회가 아니며 개선이 전혀 없다는 동등성 증명도 아니다. 철회한 후보의 효과와 기존에 채택한 TEXT 범위 조회 개선을 한꺼번에 취소하지 않았다.

### 원인을 확정하지 못하게 한 측정 경계

처음 외부 진단은 전체 프로세스 CPU sample과 syscall 시간을 관측했다. 설정·측정·종료·재개방 audit가 포함된 경계이므로 요청 하나의 비용으로 볼 수 없었다. user CPU sample에는 kernel·일부 libc·대기가 충분히 귀속되지 않았고, 여러 thread의 누적 syscall wall time은 전체 elapsed와 중복될 수 있었다.

perf 실행 파일 탐색 실패를 실제 CPU 관측 성공으로 기록하지 않았다. 탐색을 고친 뒤 얻은 자료를 별도로 남겼다. strace의 system time과 후속 wall-clock 시간도 같은 지표로 덮어쓰지 않았다. 상속된 최대 RSS가 엔진 메모리 사용량처럼 보이는 문제를 확인한 뒤 그 수치로 메모리 우위를 판단하지 않았다.

이 한계 때문에 요청 경계를 가진 별도 진단 모드를 도입했다. [배포 제외 계측 구현](https://github.com/woonyong-choi/totedb/pull/240)은 wall·thread CPU·단계·I/O를 연결하지만, 계측의 실행 비용 자체도 존재한다. 따라서 ON을 최종 성능 조건으로 쓰지 않고 OFF와 분리했다. 지연을 일부러 넣은 실험이 아니다.

### 계측 도구 자체를 검증한 과정

도구의 출력이 그럴듯하다는 것만으로 원인 분석의 근거가 되지는 않는다. 독립 검토에서 버퍼가 찬 뒤 마지막 요청들이 누락되면 다음 요청 없이 drop을 보고하지 못하는 경로를 찾았다. 종료 시 drain과 부분 drain의 손실 수를 검사해 고쳤다.

strip된 ELF에서 일반 심볼 표가 비어도 동적 계측 심볼이 남을 수 있었다. 배포 검사에 동적 심볼 확인을 추가하고 실제 Linux strip fixture로 확인했다. Python 참조 비교를 실행하는 과정에서는 패키지·헤더 버전과 stale 공유 라이브러리의 불일치를 발견했다. 공개 헤더 변경의 빌드 의존성을 보완해 재빌드를 검증했다.

이 수정은 제품 처리량 개선 실험의 결과가 아니다. 측정·배포 도구가 잘못된 성공을 보고하는 경로를 차단한 검증이다. 과거 버전의 건너뛴 시험을 나중의 성공으로 소급해 바꾸지 않았다.

### 이번 실험으로 이어진 질문

이번에는 먼저 경합 없는 C UPDATE와 SQLite prepare-each·prepared-reuse를 비교한다. 이 결과는 SQL 준비 정책과 commit 경계를 드러내지만 실제 큐의 성능을 대신하지 않는다. 다음으로 공식 YCSB의 요청 종류·행 규모를 비교하고, 큐에서는 업무 종류·payload·역할별 클라이언트 수를 바꾼다. 내부 비용은 별도 ON 진단에서만 확인한다.

후속 가설은 관측된 단계가 크다는 이유만으로 채택하지 않는다. 예를 들어 파싱 시간이 관측돼도 parse cache를 제거한 동일 조건의 반사실 비교 없이는 cache의 개선량을 알 수 없다. fsync wall time이 관측돼도 그것이 SQLite와의 전체 격차를 만든 유일한 원인은 아니다. 단계별 직접 관측과 아직 분리하지 못한 잔여를 함께 보고한다.

## 새 관측에서 생긴 후속 가설

아래는 결과를 본 뒤 생성한 탐색적 가설이다. 이번 표본으로 사전 검증한 가설이나 구현 결정을 뜻하지 않는다.

| 관측과 근거 | 가능한 설명 | 아직 반박하지 못한 대안 | 다음 확인 방법 |
|---|---|---|---|
| native에서는 DELETE/FULL보다 높은 처리량, 큐에서는 WAL/FULL보다 낮은 조건 다수 | SQL 처리 자체보다 commit 구성과 업무당 쓰기 횟수의 영향이 클 가능성 | 스키마·문장 cache·바인딩·행 수가 동시에 다름 | 같은 C UPDATE에 SQLite WAL 조건을 추가하고 업무별 실제 commit 수를 대응 |
| ON 단일 행 UPDATE에서 fsync wall이 가장 큰 관측 단계 | 이 작은 durable 쓰기는 저장 완료 대기의 영향이 큼 | 공유 host·가상 디스크·스케줄링 대기, 계측 교란 | 별도 장치·표본과 동일 내구성의 요청 경계·OS 추적을 연결 |
| YCSB C의 큰 행 규모에서 낮은 상대 처리량 | 키 조회·결과 복원·바인딩 비용의 누적 가능성 | 캐시·JVM·실제 키 분포·준비 정책 차이 | 읽기 요청의 단계·방문량·반환 바이트를 같은 입력으로 분리 |
| mixed에서 worker 증가와 처리량 감소·claim tail 증가를 함께 관측 | 단일 writer 아래 재시도·스케줄링·업무 순서가 비용을 추가할 가능성 | 작은 backlog와 Python 프로세스 경쟁, 고정 clock·배정 불균형 | 동일 작업량의 client 수·BUSY·sleep·완료 분포와 request trace를 연결 |
| 단일 행 증가에도 반복 쓰기 바이트가 발생 | COW 게시·메타데이터 쓰기 단위의 영향 가능성 | 커널 페이지 cache와 장치 쓰기량은 별도 | 트랜잭션 묶음 크기별 논리 변경 바이트·syscall 바이트·장치 I/O 구분 |

이 결과로 파서 cache·fsync 생략·WAL 전환·다중 writer를 곧바로 채택하지 않는다. 특히 장치와 내구성 보장을 바꾸면 이번 비교와 다른 실험이 된다. 후속 성능 판단은 [#239](https://github.com/woonyong-choi/totedb/issues/239), 다중 writer의 안전성은 [#238](https://github.com/woonyong-choi/totedb/issues/238)에 연결한다.

## 위험 요소 점검

| 위험 요소 | 이 실험에서 |
|---|---|
| 공유 VM·host 부하와 순서 | 같은 VM에서 순환·교대했다. 환경 전후와 모든 반복 범위를 보존했지만 host의 외부 부하는 통제하지 못했다. |
| 계측 교란 | ON/OFF를 분리했다. 실제 ON/OFF 비에도 차이가 보여 진단 시간으로 OFF 성능을 대체하지 않았다. |
| 바인딩·prepare·commit 차이 | native·YCSB·큐 결과를 분리했고 SQLite DELETE·WAL 및 prepare 정책을 명시했다. |
| 작은 표본·짧은 backlog | 조건당 다섯 번과 작은 작업량이다. 좁은 구간을 다른 장치의 보장으로 해석하지 않았다. |
| 내구성 의미 차이 | FULL·DURABLE 설정은 유지했지만 전원 장애 동등성·장치 flush 이행을 검증하지 않았다. |
| 실패·원자료 소실 | 초기 취소 자료와 수정 수집의 원본을 보존했다. 외부 DB까지 파일 집합·해시를 확인했다. |

## 한계

- 비계측 정상 실행과 재개방 검증이다. 새 전원 장애·복구 실험이나 대량 장기 운영 검증은 수행하지 않았다.
- native는 단일 행 UPDATE·SQLite DELETE/FULL 조건이다. 큐의 WAL 비교와 같은 점수로 취급할 수 없다.
- native에는 요청별 지연 분포 대신 타이머 합계가 있다. YCSB·큐의 p99와 직접 비교하지 않는다.
- 성공한 YCSB trial DB는 기존 수집기의 정책대로 정리되며 저장 audit를 남겼다. baseline·실패 DB와 별도로 존재하는 DB는 artifact에서 검증했다.
- RSS에는 기존 상속 고수위 문제를 배제할 새 근거가 없어 엔진 메모리 우위의 판정에 사용하지 않았다.
- CPU와 wall은 다른 축이고 request·상위 단계·syscall inclusive 시간은 겹친다. 이들을 더해 병목 기여율 합계로 만들지 않았다.
- 여러 탐색적 구간을 보정 없이 비교했다. 단일 조건의 우위를 DB 전체의 승리로 일반화하지 않는다.

## 재현 방법

원자료·DB·로그·실제 binary는 `release-cost-evidence` artifact에 있다. 공개 Git에는 계획·수집기·요약·환경·해시와 출처를 보존했다. [원자료 안내](data/README.md)의 파일 역할과 보존 만료 조건을 먼저 확인한다.

```sh
gh run download 39236890565 --repo woonyong-choi/totedb \
  --name release-cost-evidence --dir build/release-cost-evidence
export RELEASE_COST_DATABASE_ROOT="$PWD/build/release-cost-evidence"
export OUTPUT="$RELEASE_COST_DATABASE_ROOT/build/release-cost"
RUN_ID=20261019T102202Z-c595a64-check bash docs/experiments/release-cost/run.sh verify
RUN_ID=20261019T102202Z-c595a64-check bash docs/experiments/release-cost/run.sh analyze
cmp "$OUTPUT/results/summary.json" docs/experiments/release-cost/results/summary.json
```

`RELEASE_COST_DATABASE_ROOT`는 내려받은 DB 검증 전용이다. 새 collect/all에 남겨 두면 수집기가 거절한다. 같은 로그 이름은 덮어쓰지 않으므로 반복 검증에는 새 RUN_ID를 사용한다. 새 수집은 이 변수를 해제한 뒤 새 출력 경로에서 수행한다.
